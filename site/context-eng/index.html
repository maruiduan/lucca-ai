    上下文工程：给智能体管好「眼前这页纸」

    第二部分 · 智能体 · 第 3 篇　|　约 15 分钟　|　4 个小实验

    一句话结论模型每一步只能看到上下文里的那些字。智能体一转起来，工具结果、聊天记录越堆越多：又贵、又慢、还会让它变糊涂。上下文工程就是每一步都替它决定放什么、丢什么、压成什么样。Anthropic 的说法是：找到最少、但信息量最高的那一组 token。

    01从「写好提示词」到「管好上下文」

    第一部分的第 4 篇讲过三件事：模型没有记忆，每一轮都把整段上下文从头读一遍；上下文有窗口上限；比措辞更重要的是往里面放什么。那一篇说的主要是「一问一答」时怎么写提示词。

    到了智能体，情况变了。上一篇的循环每转一圈，就往上下文里追加一段想法和一段工具结果。一个修 bug 的任务可能转上百圈，读几十个文件、跑几十次命令。这时候问题不再是「提示词怎么写」，而是：这么多东西，下一步该让模型看到哪些？

    2025 年，业界开始用「上下文工程」（context engineering）来叫这件事。Anthropic 在《Effective context engineering for AI agents》里的定义是：在模型每一次推理时，挑选并维护最合适的一组 token。它包括系统提示，也包括工具说明、外部数据、历史消息……所有会进入窗口的东西。而且它不是写一次就完事，每一步都要重新挑。

    02智能体的上下文是怎么被塞满的

    拖动下面的滑块，看一个编程智能体干活时，上下文里各部分怎么增长。每一圈它都要把整段重新读一遍，所以读过的 token 总数（也就是你付的钱）比窗口本身涨得快得多：

    小实验 ①：上下文预算示意数字
    已经转了 10 圈
    系统提示工具说明书项目说明对话与想法工具结果摘要
    当前上下文—
    窗口上限200K
    累计读过的 token—

    ⚠️ 示意数字：假设系统提示 3K、工具说明书 12K、项目说明 4K，每圈新增想法约 0.8K、工具结果约 6K（瘦身后约 1.5K）；窗口按 200K 算，压缩在 160K 时触发、压成 8K 摘要。真实系统差别很大，而且很多服务对重复出现的开头部分有缓存折扣，这里没算。

    几个直观的结论：工具结果是大头；就算窗口没满，每一圈的成本也在变高；什么都不做，几十圈后就会撞上限。Anthropic 在讲多智能体研究系统时给过一组数字：在他们的数据里，智能体用的 token 大约是普通聊天的 4 倍，多智能体系统约 15 倍。

    03越长越糊涂

    窗口越来越大，几十万甚至上百万 token，那全塞进去不就好了？问题是：放得下，不等于看得清。

    2023 年斯坦福等机构的论文《Lost in the Middle》做了一个干净的实验：给模型 20 篇文档，只有一篇含答案，然后把这篇挪到不同位置。结果是一条 U 形曲线：答案在开头或结尾时最准，在中间时最差。拖动看看论文里 GPT-3.5-Turbo 的实测数据：

    小实验 ②：答案藏在第几篇？论文实测数据
    含答案的文档放在第 10 / 20 篇
    这个位置的准确率—
    一篇文档都不给（闭卷）56.1%

    数据来自 Liu 等（2023）表 6：GPT-3.5-Turbo，20 篇文档的多文档问答，实测位置是第 1、5、10、15、20 篇（实心点），其余位置是连线估计（空心点）。新模型的曲线更平，但规律没有消失。

    更新的研究也看到了类似现象。向量数据库公司 Chroma 在 2025 年的报告《Context Rot》（上下文腐烂）里测了 18 个模型，发现输入越长，表现越不稳定，即使任务本身很简单。Anthropic 把它比作人的工作记忆：模型有一份「注意力预算」，每多一个 token 就分走一点。第 1 篇讲过注意力是每个 token 去「看」其他所有 token，n 个 token 就有约 n² 对关系，越长越分散。

    所以实践上：最要紧的放在开头或结尾（比如任务要求在开头说一遍、结尾再提醒一遍），不相关的别放进来。

    04四种办法：写、选、压、隔

    LangChain 的一篇总结把常见做法归成四类，后面几节逐个讲：

    ✍️ 写把要紧的事记到上下文外面（笔记、待办清单），需要时再读回来。
    第 7 节     🔎 选只把这一步用得上的拿进来：按需检索文件、资料、工具。
    第 6 节     🗜️ 压快满了就做摘要；旧的工具结果清掉或截短。
    第 5、8 节     🧩 隔把子任务交给另一个智能体，在干净的上下文里做，只交回结论。

    05压：快满了就做摘要

    最常用的第一招是压缩（compaction）：上下文快满时，让模型把到目前为止的内容写成一份摘要，然后开一个新的上下文，只带着摘要继续干。Anthropic 介绍 Claude Code 的做法是：保留架构上的决定、没解决的 bug、实现细节，丢掉重复的工具输出，再附上最近读过的 5 个文件。

    难点在于留什么、丢什么。压得太狠，会丢掉一个当时看起来不起眼、后来才发现很要紧的细节。来试试：

    Anthropic 给写压缩提示词的人的建议是：先追求不漏（宁可多留），再慢慢追求精简。而最安全、最轻的一种压缩，是只把很久以前的工具原始结果清掉：调用过了、结论已经写进后面的想法里，原文就没必要一直留着。

    06选：只带「索引」，用时再翻

    第 6 篇的 RAG 是「提问前先检索好，一次性贴进来」。智能体有了工具以后，多了一种做法：即用即取（just in time）。上下文里只放轻量的「索引」：文件路径、网页链接、查询语句；真需要时，再用工具去读，而且只读需要的那一段。

    开始就全放进去即用即取
    做法把 30 个可能相关的文件全贴进来先看目录和文件名，搜关键词，只打开 3 个相关文件的相关部分
    占用大，而且大多数用不上小
    速度开始就有，快要多几步工具调用，慢一些
    风险无关内容干扰判断（第 3 节）可能漏找、走弯路

    这很像人：我们不会把整个硬盘背下来，而是靠文件夹、书签、搜索在需要时找到。文件名和目录结构本身就是线索：tests/ 下面的文件和 src/ 下面的同名文件，用途显然不同。Claude Code 用的是混合做法：项目说明文件一开始就放进来，其余代码靠搜索命令即用即取。

    07写：把要紧的记在笔记里

    上一篇模拟器里的「草稿本」就是这一招：让智能体把进度和关键信息写到上下文外面的文件里（比如一个 NOTES.md 或待办清单），上下文被压缩、甚至整个重开以后，再把笔记读回来接着干。

    # NOTES.md（智能体自己写的笔记，示例） 目标：修复导出 Excel 时日期乱码 约束：用户要求不能改公开 API 的参数 已确认：问题在 export/date.py 第 88 行，时区被丢了 已试过：改成 UTC → 测试 3 个失败（本地时间被改了），已撤回 下一步：在格式化时带上时区；跑 tests/test_export.py

    Anthropic 举过一个例子：让 Claude 玩《宝可梦》时，它会自己记下「在 1 号道路已经练了 1234 步，皮卡丘离目标还差 2 级」，画出走过的地图、记下哪些招式对哪种对手有效。上下文重置后读回笔记，就能接着进行几个小时的长任务。笔记的好处是便宜、可靠、人也看得懂。跨对话、跨天的「长期记忆」是第 7 篇的话题。

    08工具结果要瘦身

    第 2 节里，工具结果是上下文的大头。一次搜索、一次跑测试，原样返回可能就是几千上万 token，而模型真正需要的往往只有几行。所以设计工具时就要省。Anthropic 提到，Claude Code 默认把单次工具返回限制在 25,000 token 以内。来给一个工具的返回结果瘦身：

    常见的瘦身办法：只返回需要的字段，去掉内部编号、时间戳这类模型用不上的；分页和截断，并告诉模型还有多少条、怎么取下一页；出错时给一句有用的提示，而不是一整屏报错堆栈；对很长的日志，只返回开头、结尾和含 error 的行。

    09隔：让子任务在干净的上下文里干活

    最后一招是把活分出去：主智能体把一个子任务（比如「把这个代码库里所有用到日期格式化的地方找出来」）交给一个子智能体。子智能体在自己全新的上下文里搜索、阅读，可能用掉几万 token，但只交回一份 1000~2000 token 的结论。主智能体的上下文因此保持干净。

    Anthropic 的多智能体研究系统就是这么搭的：在他们的内部评测里，一个 Opus 4 主智能体带几个 Sonnet 4 子智能体，比单个 Opus 4 智能体好 90.2%；代价是 token 用量大约是普通聊天的 15 倍。什么时候值得这样分、子智能体之间怎么配合，留到第 7 篇「记忆与子任务」细讲。

    10记住这些就够了

    1. 上下文工程 = 每一步替模型决定放什么、丢什么、压成什么样。目标是最少、但信息量最高的那组 token。
    2. 上下文不是越多越好：贵（每圈都要重读）、慢，还会越长越糊涂，中间的信息最容易被忽略。
    3. 四种办法：写（笔记）、选（即用即取）、压（摘要、清理旧工具结果）、隔（子任务）。压缩要先保证不漏关键约束。
    4. 工具结果往往是大头，设计工具时就要让它返回得少而准。
