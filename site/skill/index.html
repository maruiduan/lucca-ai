    Skill：把经验写成一本「用时才翻」的说明书

    第二部分 · 智能体 · 第 5 篇　|　约 14 分钟　|　4 个小实验

    一句话结论工具让智能体「能做」，但不告诉它「怎么做才对」：你们公司的报告格式、填某种表格的步骤、某个库的坑。Skill（技能）就是一个文件夹，里面放一份 SKILL.md 说明书，可以再带上脚本和参考资料。妙处在于平时只占一两行，用到时才整本翻开。

    01为什么需要 Skill

    假设你让智能体「按我们部门的格式写周报」。它有读写文件的工具，也很会写字，但它不知道你们的格式：标题怎么写、数据放哪一节、哪些词不能用。传统做法有两种，都不理想：

    • 每次在对话里重新交代：累，而且容易漏。
    • 全写进系统提示：一次还好。但你还有报销规则、代码规范、PPT 模板、合同审核要点……几十份全塞进去，每一轮都要重读，上下文工程那篇说过的又贵又糊涂就来了。

    Anthropic 在 2025 年 10 月 16 日的文章《Equipping agents for the real world with Agent Skills》里提出的办法是：把每份经验做成一个独立的文件夹，智能体平时只知道有哪些，需要时再自己去读。好比新员工入职，不用背下整本手册，只要知道「报销的事看第 3 章」。

    2025 年 12 月 18 日，这个格式作为开放标准发布在 agentskills.io，已被越来越多的智能体产品采用。

    02一个 Skill 长什么样

    就是一个文件夹。必须有的只有 SKILL.md：

    weekly-report/ ├── SKILL.md # 必需：简介 + 说明 ├── scripts/ # 可选：可以运行的脚本 │ └── fetch_metrics.py ├── references/ # 可选：更详细的参考资料 │ └── style-guide.md └── assets/ # 可选：模板等 └── template.docx

    SKILL.md 开头是一小段 YAML「封面」，下面是正文：

    --- name: weekly-report description: 按市场部格式撰写周报。用户提到"周报"、 "本周总结"或需要汇报每周数据时使用。 --- # 写周报 1. 先运行 scripts/fetch_metrics.py 拉取本周数据 2. 按 assets/template.docx 的四节结构写： 本周结果 / 关键数据 / 风险 / 下周计划 3. 措辞要求见 references/style-guide.md （只有需要核对措辞时再读）

    封面只有两个必填项：name（最多 64 个字符，只能用小写字母、数字和连字符）和 description（最多 1024 个字符，写清楚做什么、什么时候用）。正文就是写给智能体看的普通说明，可以引用文件夹里的其他文件。

    注意 scripts/：有些事用代码做比让模型「想」更可靠，比如从 PDF 里抽表格、算一组数据。Skill 可以附带脚本，智能体直接运行它，只把结果读进上下文，脚本本身的代码不用占地方。

    03三层渐进披露：省下上下文的关键

    规范把这叫做「渐进披露」（progressive disclosure），分三层：

    1. 第一层：封面。启动时，所有已安装 Skill 的 name 和 description 进入上下文，每个约 100 token。
    2. 第二层：正文。智能体判断某个 Skill 用得上时，才读整份 SKILL.md。规范建议正文不超过 5000 token、500 行以内。
    3. 第三层：附件。正文里提到的参考资料、脚本、模板，真要用时才读或运行。
    小实验 ①：装了很多 Skill，上下文会被撑爆吗示意数字
    已安装 20 个 Skill
    全部塞进系统提示
    渐进披露
    其他上下文Skill 封面Skill 正文附件
    全部塞进去—
    渐进披露—

    ⚠️ 示意数字：每个封面按规范说的约 100 token，正文按 3000 token、参考资料按 4000 token 估，其他上下文按 20K、窗口按 200K。

    这意味着 Skill 可以装很多而几乎不占地方，单个 Skill 也可以带很多资料，因为没用到的部分不花钱。Anthropic 原文举的例子是 PDF 技能：SKILL.md 讲常用操作，填表这种少见的需求单独放在 forms.md，只有用户要填表时才读。

    04智能体怎么知道该翻哪本

    没有什么魔法：模型看着上下文里那一排封面，根据 description 自己判断该读哪个，然后用读文件的工具去打开它。所以 description 写得好不好，直接决定 Skill 会不会在该用的时候被用上。

    小实验 ②：同样的请求，描述写法不同模拟

    ⚠️ 这里用「请求和描述有没有共同的关键词」来模拟模型的判断，真实模型理解得更灵活，但「描述含糊就容易选错或不选」这一点是一样的。

    规范给的建议正是如此：description 要同时写「做什么」和「什么时候用」，并带上用户可能说的关键词。

    小实验 ③：检查 SKILL.md 的封面按规范校验

      规范还要求 name 和文件夹名一致。写正文时的经验：只写模型不知道的东西（你们的规矩、具体步骤、容易出错的地方），别教它「什么是周报」；长的参考资料拆到单独文件里，正文里写清楚「什么情况下去读哪个文件」。

      ⚠️ Skill 里可以放脚本，装一个来路不明的 Skill 等于让智能体运行别人的代码、听别人的指令。和 MCP 服务器一样，只装可信来源的。

      06Skill、MCP、提示词、子智能体怎么选

      它们经常一起出现，但解决的问题不同：

      东西解决什么一句话
      MCP能连上什么给智能体新的「手」：接外部服务
      Skill怎么做才对给智能体按需翻阅的「手册」
      系统提示每次都要遵守的永远在场的几句话，越短越好
      子智能体别弄脏主上下文派出去干活、只交回结论（第 7 篇）

      07记住这些就够了

      1. Skill = 一个带 SKILL.md 的文件夹，可附带脚本、参考资料、模板。2025 年 10 月由 Anthropic 提出，12 月成为开放标准。
      2. 核心是渐进披露：封面（约 100 token）常驻，正文用时才读，附件要用时才读。装很多也不撑爆上下文。
      3. 智能体靠 description 决定翻哪本，所以要写清「做什么 + 什么时候用」。
      4. MCP 给「手」，Skill 给「手册」。来路不明的 Skill 和服务器一样别乱装。
